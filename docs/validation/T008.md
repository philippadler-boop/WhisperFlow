### 1. Real `whisperflow transcribe --help`, raw bytes captured to disk

Ran the actual installed console script (not `python -m`, not
`CliRunner`) with a wide terminal width and output/error redirected
separately to files, so the raw bytes on disk are exactly what the
process wrote:

```
$ COLUMNS=220 whisperflow transcribe --help > help_output_raw.txt 2> help_output_stderr.txt
EXIT:0
stderr: (empty)
```

First attempt at inspecting the raw bytes surfaced a genuine environment
wrinkle worth recording: Python's stdout encoding when redirected to a
file on Windows defaults to the console's legacy codepage (cp1252 here),
not UTF-8, when no real TTY is attached. Byte-inspecting that first
capture showed the em dash as a single byte `\x97` (cp1252's own em-dash
codepoint — correct once you know the encoding, but not directly
comparable to the contract file's UTF-8 bytes). To get a byte-for-byte
comparable capture, re-ran with `PYTHONIOENCODING=utf-8` forced:

```
$ PYTHONIOENCODING=utf-8 COLUMNS=220 whisperflow transcribe --help > help_output_utf8.txt
EXIT:0
```

Raw rendered panel (Rich picked full Unicode box-drawing characters once
UTF-8 was confirmed, vs. ASCII `+`/`-`/`|` fallback in the cp1252 run —
same text content either way):

```
┌─ Options ────────────────────────────────────────────────────────...
│ --model                      <tiny|base|small|medium|large>  faster-whisper model size — smaller is faster, larger is more accurate (research.md). [default: base]
│ --review      --no-review                                    With --review, after generating a draft .srt the command opens it in $EDITOR (or --editor) and waits for confirmation before finalizing (FR-009, FR-010,
│                                                              User Story 2). --no-review finalizes immediately — for scripting/automation.
│                                                              [default: review]
```

**PASS** — exit code `0`, stderr empty, real console-script output
captured as raw bytes on disk (not read-and-trusted from any test file).

### 2. Codepoint-level comparison of the two dash-sensitive spots (independent of the reviewer's method and the test's own normalizer)

Extracted the exact `--model` and `--review` table rows directly from
`contracts/cli.md`'s raw bytes and enumerated every non-ASCII character
in each row by codepoint:

```
MODEL row:  1 non-ASCII char -> U+2014
REVIEW row: 1 non-ASCII char -> U+2014
```

Then did the same on the UTF-8-forced `--help` capture from step 1,
searching around `"model size"` and `"immediately"`:

```
near 'model size':   codepoint=U+2014   (...size \u2014 smaller is faster...)
near 'immediately':  codepoint=U+2014   (...immediately \u2014 for scripting...)
```

Both spots in the real `--help` output are codepoint-identical
(`U+2014`, EM DASH) to both spots in the contract file — confirmed via
`ord()` on decoded Python strings, not by visual comparison of rendered
glyphs (rendered glyphs for `U+2014` display as a literal replacement
character `�` in this shell's own output encoding, which is exactly the
kind of visual trap the task warns about — codepoint inspection sidesteps
it entirely).

Wrote an independent normalization function (not copied from
`tests/contract/test_cli_contract.py::_normalize`, though structurally
similar since the underlying problem — strip Rich's box-drawing/ANSI
decoration, collapse wrapped whitespace — is the same) and checked every
row of `contracts/cli.md`'s Arguments/Options tables as an exact
substring of the real `--help` output. First pass produced one false
failure (`<tiny|base|small|medium|large>` "missing") that turned out to
be a bug in my own throwaway normalizer (it stripped ASCII `|` globally,
including the literal pipes inside the enum's own choice-set syntax, not
just table-border pipes); fixed to strip only the Unicode box-drawing
block (`U+2500`–`U+257F`) instead, after which all 17 checked phrases —
including both em-dash phrases, the enum literal, both `[default: ...]`
annotations, and every FR/User-Story citation — passed as exact
substrings. Also explicitly checked for the two specific historical
regressions and found neither: no `" -- "` (ASCII double-hyphen) at
either dash location, and no stray literal `(default)` anywhere in the
output.

**PASS** — both dash-sensitive spots verified at the raw-byte/codepoint
level against the contract's raw bytes, using a normalization method
written independently of the one under test, with a self-caught and
corrected bug in that independent method along the way (recorded above
for transparency, not swept under the rug).

## Evidence

### 1. Real `ffprobe`, real fixture videos, no mocking

First probed both fixtures with the raw `ffprobe` CLI directly (independent
of any Python code) to know what the "ground truth" values should be:

```
$ ffprobe -v error -print_format json -show_format -show_streams tests/fixtures/clear_speech.mp4
...
"format_name": "mov,mp4,m4a,3gp,3g2,mj2", "duration": "3.491020" ...
streams: [video h264, audio aac] (has an audio stream)

$ ffprobe -v error -print_format json -show_format -show_streams tests/fixtures/silence.mp4
...
"format_name": "mov,mp4,m4a,3gp,3g2,mj2", "duration": "3.000000" ...
streams: [video h264, audio aac] (has an audio stream — silence.mp4 has a
silent but present audio track, distinct from no audio track at all)
```

Then imported and called `probe_video()` directly (no `subprocess` mock,
real `ffprobe.exe` resolved via `where ffprobe` →
`C:\ProgramData\chocolatey\bin\ffprobe.exe`):

```python
from audio.video_probe import probe_video
from pathlib import Path

for name in ["clear_speech.mp4", "silence.mp4"]:
    p = Path("tests/fixtures") / name
    v = probe_video(p)
    print(name, "->", v)
```

Output:

```
clear_speech.mp4 -> Video(path=WindowsPath('tests/fixtures/clear_speech.mp4'), container_format='mp4', duration_seconds=3.49102, has_audio_track=True)
silence.mp4 -> Video(path=WindowsPath('tests/fixtures/silence.mp4'), container_format='mp4', duration_seconds=3.0, has_audio_track=True)
ALL REAL-FIXTURE CHECKS PASSED
```

Both `duration_seconds` values match the raw `ffprobe` ground truth
exactly (`3.491020` → `3.49102`, `3.000000` → `3.0` as floats),
`container_format` correctly resolves to `mp4` (both files have a `.mp4`
extension inside the mp4/mov shared demuxer, correctly disambiguated), and
`has_audio_track` is `True` for both, matching the real stream table.

**PASS** — real container_format/duration_seconds/has_audio_track values
come back from the real binary and are sensible and independently
cross-checked against raw `ffprobe` output.

### 2. Independently-constructed collision scenarios (`UnsupportedVideoFormatError`)

Designed five scenarios from scratch by reading `_detect_container_format`'s
branch logic myself (not copied from `tests/unit/test_video_probe.py`,
which I read only afterward, for comparison — see note below), each driving
`probe_video()` through a `subprocess.run`/`shutil.which` mock written
independently of the test file's own `_ffprobe_result` helper:

| Scenario | Input | Expected | Actual |
|---|---|---|---|
| A: mp4/mov container mislabeled `.mkv` | `renamed_movie.mkv`, `format_name="mov,mp4,m4a,3gp,3g2,mj2"` | reject, `detected_format=None` | **PASS** — raised `UnsupportedVideoFormatError`, `detected_format=None`, message `"could not determine a supported video format for 'renamed_movie.mkv' (supported formats: mp4, mov, mkv)"` |
| B: genuine `.3gp` sibling (shares mp4/mov demuxer) | `clip.3gp`, same `format_name` | reject, `detected_format="3gp"` | **PASS** — raised, `detected_format='3gp'` |
| C: literal `format_name="mkv"` token on a `.mp4`-named file | `sample.mp4`, `format_name="mkv"` | reject, `detected_format=None` | **PASS** — raised, `detected_format=None` |
| D (negative control): genuine `.mkv` file, real matroska demuxer | `real_movie.mkv`, `format_name="matroska,webm"`, `duration=42.0` | **accept** as `mkv` | **PASS** — `Video(container_format='mkv', duration_seconds=42.0, has_audio_track=True)`, not rejected |
| E: genuinely ambiguous mp4-vs-mov demuxer with an unrelated `.avi` extension | `old.avi`, `format_name="mov,mp4,m4a,3gp,3g2,mj2"` | reject, `detected_format="avi"` | **PASS** — raised, `detected_format='avi'` |

All five matched my own hand-derived expectations exactly before running
anything (worked through the six return sites of
`_detect_container_format` on paper first, then confirmed by execution).
Scenario D is a deliberate negative control to confirm the collision
guards from rounds 2–4 don't over-reject genuine `.mkv` input. Comparing
against `tests/unit/test_video_probe.py` afterward: scenarios A/B/C
exercise the same defect classes as
`test_mkv_extension_with_mp4_mov_family_container_is_rejected`,
`test_3gp_extension_and_shared_mp4_demuxer_is_rejected`, and
`test_literal_mkv_format_name_token_is_rejected` respectively, but with
different concrete filenames/durations and a hand-rolled mock rather than
the shared `_ffprobe_result` helper — an independent construction, not a
copy, arriving at the same conclusion the existing tests do.

**PASS** — `UnsupportedVideoFormatError` is genuinely raised for every
constructed ambiguous/unsupported input, and genuine `.mkv` input is still
correctly accepted (no over-rejection introduced by the five rounds of
collision fixes).

### 3. `MaxDurationExceededError` and `FfmpegNotFoundError`, independently forced

Four independently-mocked scenarios (`subprocess.run`/`shutil.which`
patched directly, not via the test file's fixtures):

| Scenario | Condition | Result |
|---|---|---|
| Over-cap duration | `duration = 7200.0 + 137.0 = 7337.0`s (2:02:17) on an otherwise-valid mp4 | **PASS** — raised `MaxDurationExceededError`, `duration_seconds=7337.0`, `max_duration_seconds=7200.0`, message `"video exceeds maximum supported length of 2 hours (got 2:02:17)"` |
| Negative control: exactly at cap | `duration = 7200.0`s exactly | **PASS** — accepted, `Video(duration_seconds=7200.0, ...)`, no exception (confirms the data-model.md "≤ 7200s" boundary is `>`, not `>=`) |
| Missing binary | `shutil.which("ffprobe")` mocked to return `None` | **PASS** — raised `FfmpegNotFoundError`, `executable='ffprobe'`, message `"required 'ffprobe' binary was not found on PATH (install ffmpeg and ensure it is on PATH)"` |
| Binary vanishes mid-call (race) | `shutil.which` returns a fake path, but `subprocess.run` mocked to raise `FileNotFoundError` | **PASS** — raised `FfmpegNotFoundError`, same message, confirming the documented race-condition handling around the `subprocess.run` call actually works |

**PASS** — both error types are genuinely raised under their respective
real conditions, not merely asserted by the test suite; the exactly-at-cap
boundary was independently checked and correctly does *not* raise.

## What is actually being validated here

This task's real outcome is **not** "the SC-002/SC-006 timing question is
resolved" and **not** "the default model changed." The evidence trail
shows the opposite arc: an unattended developer changed the default to
`tiny` based on short-fixture CI benchmarking; a reviewer correctly
identified that evidence as methodologically too weak to justify the
change (short-clip timing dominated by fixed overhead, no fixture in the
repo backing the claimed numbers, direct conflict with a real ~59-minute
video finishing at `--model base` in 48.7s — ~35x inside target — and no
SC-003 accuracy measurement of `tiny` vs. `base` at all); the developer's
follow-up commit reverted the default to `base` and rewrote the
documentation to honestly state the conflict rather than assert a false
resolution in either direction.

So the requirement actually being validated is: **the CLI's real behavior
matches what is now documented, and the documentation honestly represents
an unresolved conflict** — neither overclaiming that `base` is proven fine
everywhere, nor overclaiming that `tiny` is required, nor hiding the real
59-minute/48.7s data point that contradicts the short-fixture numbers.

### (b) Documentation honesty — `contracts/cli.md` and the ADR entry, read critically

Read `specs/001-video-subtitle-generator/contracts/cli.md`'s
"Minimum-hardware note (SC-002/SC-006, T029)" section and the new T029
paragraph appended to `docs/adr/0001-local-asr-engine.md`'s Consequences,
in full, specifically checking for over/understatement:

- Both documents state the short-fixture result (`base` sometimes missed
  the ~2x-real-time target on a ~3.5s clip, `tiny` consistently met it)
  **and** immediately qualify it as methodologically weak (fixed
  per-run overhead dominates a 3.5s clip; not representative of
  steady-state decode throughput).
- Both documents state the conflicting real-world data point in full,
  with the actual number: the ~59-minute video finishing at `--model
  base` in 48.7s, ~35x inside target — this is the specific number a
  dishonest rewrite could have been tempted to soften or omit, and it is
  present, unhedged, in both files.
- Both explicitly say SC-003 accuracy cost of `tiny` vs. `base` "has not
  been measured" — this is not glossed over or implied to be fine.
- Neither document declares the conflict resolved. `contracts/cli.md`
  says "Given that unresolved conflict, `base` remains the CLI default"
  and recommends `tiny` only as a fallback for constrained/CPU-only
  hardware, explicitly telling the reader to verify with
  `scripts/benchmark.py time` on their own machine rather than asserting
  a universal answer. The ADR entry says "properly reconciling this
  conflict ... is left as follow-up work rather than changing the default
  on the current evidence."
- No claim in either document is falsified by anything independently
  observed in this validation (see (c) below): the fixture is genuinely
  ~3.5s (confirmed via `ffprobe`), and independently re-running the
  benchmark against it shows exactly the kind of noisy, borderline timing
  the documents describe, not a clean pass or fail.

This reads as an accurate, non-overclaiming representation of a genuinely
unresolved conflict — it neither asserts `base` is proven safe everywhere
nor asserts `tiny` is required, and does not hide the 59-minute/48.7s
data point. **PASS.**

### (c) Independent benchmark data point (`scripts/benchmark.py time`, this machine)

Confirmed fixture duration directly (not trusting the doc's "~3.5s"
claim):

```
$ ffprobe -v error -show_entries format=duration -of default=noprint_wrappers=1 tests/fixtures/clear_speech.mp4
duration=3.491020
```

Ran `scripts/benchmark.py time` against `tests/fixtures/clear_speech.mp4`
at both model sizes, several times each to check noise (this machine: a
Windows 11 laptop, CPU-only, no dedicated GPU used by faster-whisper here
— comparable in kind, not claimed identical, to the "reference hardware"
described in the docs):

```
$ python scripts/benchmark.py time tests/fixtures/clear_speech.mp4 --model base
Elapsed: 1.6s   SC-002/SC-006: within target (1.6s elapsed vs. 1.7s target)
$ python scripts/benchmark.py time tests/fixtures/clear_speech.mp4 --model base   (rerun)
Elapsed: 1.6s   within target (1.6s vs. 1.7s target)
$ python scripts/benchmark.py time tests/fixtures/clear_speech.mp4 --model base   (rerun)
Elapsed: 1.6s   within target (1.6s vs. 1.7s target)
$ python scripts/benchmark.py time tests/fixtures/clear_speech.mp4 --model base   (rerun)
Elapsed: 1.5s   within target (1.5s vs. 1.7s target)

$ python scripts/benchmark.py time tests/fixtures/clear_speech.mp4 --model tiny
Elapsed: 1.4s   within target (1.4s vs. 1.7s target)
```

On this specific machine, `base` happened to land within target on every
run (1.5s–1.6s elapsed against a 1.7s target), while `tiny` was faster
still (1.4s) — margins of roughly 0.1–0.2s either side of the target line
on a ~1.6s-average run. This is **not** a reproduction of the original
"base sometimes misses the target" CI result (this machine didn't
reproduce a miss in 4 runs), but it is exactly the kind of
razor-thin/noisy margin (single-digit tenths of a second on a ~3.5s clip)
that both documents describe as making the short-fixture result an
unreliable signal for steady-state throughput — a small change in
machine load could plausibly tip an individual run either side of the
"target" line. This independently corroborates the documents' central
claim that the short-fixture number is noise-dominated and not a solid
basis for a default-model decision, without resolving (or needing to
resolve) which model size is "correct" — that question remains explicitly
open, as documented. `--model` accepted both `tiny` and `base` correctly
and produced valid output in both cases, confirming the option itself
works for both values. **Independent data point obtained; does not
resolve, and was not intended to resolve, the underlying SC-002/SC-006
question.**

## Overall: PASS

This validates that T029's actual outcome — "leave the default as `base`,
but replace a methodologically weak conclusion with an honest,
non-overclaiming record of an unresolved SC-002/SC-006 vs. real-world-data
conflict" — is genuinely what shipped. The CLI's live `--help` output, the
contract doc, and the ADR entry all agree with each other and with what's
actually in `src/cli/main.py`; none of them try to paper over the
conflicting 59-minute/48.7s data point or claim a resolution that hasn't
happened. An independent benchmark run on this machine did not reproduce
the original "base misses target" result, but did reproduce the kind of
tight, noise-sensitive margin that is the documented reason not to trust
that short-fixture signal — consistent with, not contradicting, what's
written. All 369 tests in the suite pass with no regressions.

**Explicitly not resolved by this validation, and not claimed to be**:
whether `base` genuinely meets SC-002/SC-006 on real constrained
CPU-only/consumer hardware over long-form video, and what SC-003 accuracy
cost `tiny` carries relative to `base`. Both are correctly left as open
follow-up work by the documentation under review, not something this
report or the underlying PR resolves.

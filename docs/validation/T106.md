## Requirement

> T106: Replace `reviewer-agent`'s `if: false` placeholder (T103) with the
> real trigger condition: `on: pull_request: types: [opened, synchronize]`,
> scoped by `if: github.event.sender.login == '<bot login from T102>' &&
> github.event.sender.type == 'Bot'` in
> `.github/workflows/claude-agents-pipeline.yml` (ADR 0009, FR-007's
> actor-identification principle applied to `sender`).

Plus the PR's own additional, reviewer-scrutinized claim: an extra
`github.event_name == 'pull_request'` guard is required beyond ADR 0009's
literal text, because this workflow's `on:` block is shared across three
event types and a bare `sender` check would also match
`pull_request_review` events that `qa-agent`'s future trigger (T116) needs
to own exclusively.

This decomposes into 6 checkable sub-requirements:

1. `pull_request: types: [opened, synchronize]` is present in the
   workflow-level `on:` block, and the pre-existing `issues`/
   `pull_request_review` triggers are untouched.
2. `reviewer-agent`'s `if:` is no longer `if: false` and is exactly
   `github.event_name == 'pull_request' && github.event.sender.login ==
   'claude[bot]' && github.event.sender.type == 'Bot'`.
3. The `event_name` guard is structurally necessary (not decorative) given
   the shared `on:` block, and mirrors an existing, working precedent
   (`dev-agent`'s own `if:` already event_name-guards each of its two
   conditions).
4. `dev-agent`'s own trigger condition is genuinely unchanged.
5. `qa-agent`'s placeholder (`if: false`, T104/T116) is untouched — T106 is
   scoped to `reviewer-agent` only.
6. Real, observed evidence (not assumption) that the actor check correctly
   excludes a non-bot push/event, from this PR's own GitHub Actions run
   history — plus test suite and lint pass with no regressions.

### 3. `event_name` guard — structurally necessary, with working precedent

This workflow's `on:` block (confirmed above) is genuinely shared across
`issues`, `pull_request_review`, and `pull_request` — GitHub Actions has no
per-job `on:` key, so every job's `if:` is evaluated for every one of these
event types, and `sender` is present on all three payload types (issues,
pull_request_review, and pull_request events all carry a top-level
`sender`). Without the `event_name` guard, `reviewer-agent`'s `if:` would
also evaluate to true on a `pull_request_review` event sent by
`claude[bot]` — exactly the event `qa-agent`'s own future trigger (T116)
needs to own exclusively once `reviewer-agent` starts posting reviews as
that same identity (Phase 4/T113). This is a real, load-bearing gap in a
bare-`sender` condition, not a redundant defensive check.

The precedent the review round cited (`dev-agent`'s own trigger already
event_name-guarding each condition) is confirmed genuinely present and
unchanged:

```
dev-agent if: "(github.event_name == 'issues' && github.event.label.name == 'claude-dev') ||
(github.event_name == 'pull_request_review' && github.event.review.state == 'changes_requested')
"
```

Both of `dev-agent`'s two `||`-joined branches independently guard on
`github.event_name` before checking a payload-specific field
(`label.name`, `review.state`) — the identical pattern `reviewer-agent`'s
new `if:` now applies (`event_name` before `sender.login`/`sender.type`).
This is not a new, untested pattern invented for this PR; it is the same
shape as logic that has been running in this exact file since before this
PR. **PASS.**

## Requirement

> T108 [US1] Add a `Fetch PR diff` step to `reviewer-agent`: run `gh pr
> diff <PR_NUMBER>`, write the output to `GITHUB_OUTPUT` via a randomly
> generated (not fixed) heredoc delimiter, following the exact
> `env:`-then-`"$VAR"` pattern the existing "Build prompt for this
> trigger" step already uses for attacker-controlled text, in
> `.github/workflows/claude-agents-pipeline.yml` (ADR 0005 Decision 2,
> Consequences — injection-safety requirement)

ADR 0005 Decision 2 / Consequences (source of truth, cross-checked before
validating):

> a dedicated `Fetch PR diff` step runs `gh pr diff <PR_NUMBER>` ... and
> writes the output to `GITHUB_OUTPUT` as a multiline value, following the
> exact `env:`-then-`"$VAR"`-inside-heredoc pattern the "Build prompt for
> this trigger" step already uses — with a **randomly generated** heredoc
> delimiter ... The diff text is attacker-controlled to the same degree as
> issue titles and review bodies already are. The `Fetch PR diff` step
> MUST follow the existing `env:`-then-`"$VAR"`-in-heredoc pattern with a
> **randomized** delimiter; it MUST NOT splice `gh pr diff` output into a
> `run:` script body via `${{ }}` under any circumstance ... If the `Fetch
> PR diff` step fails or returns empty ... the workflow MUST fail visibly
> per FR-013 rather than invoking `reviewer` with an empty or missing
> diff and letting it guess.

This decomposes into the following checkable sub-requirements:

1. The step runs `gh pr diff <PR_NUMBER>` with context values (`REPO`,
   `PR_NUMBER`, `GH_TOKEN`) passed via `env:`, never spliced via `${{ }}`
   into the `run:` script body.
2. The captured diff is referenced only as `"$DIFF"` inside a heredoc —
   never re-spliced any other way — and **hostile content in the diff is
   never executed**, appears verbatim as inert data, and does not corrupt
   the `GITHUB_OUTPUT` file's structure (the adversarial crux of this
   task).
3. Empty `gh pr diff` output causes a non-zero exit and nothing written to
   `GITHUB_OUTPUT` (FR-013).
4. A failing `gh pr diff` invocation causes the step to fail visibly
   (propagates through `bash -eo pipefail`), not silently continue.
5. The heredoc delimiter is generated fresh at runtime and differs across
   runs, not a fixed string.
6. `tests/unit/test_reviewer_agent_fetch_pr_diff.py` genuinely passes.
7. No regressions in the full suite (418 tests) or lint.

### 4. `gh` failure path

Fake `gh` that writes to stderr and exits 1 (simulating a real API
error), run under the same `bash -eo pipefail` semantics GitHub Actions
uses for `run:` steps on `ubuntu-latest`:

```
$ PATH="$(pwd)/bin_fail:$PATH" \
  GH_TOKEN=fake-token REPO=owner/repo PR_NUMBER=180 \
  GITHUB_OUTPUT="$(pwd)/gh_output_fail.txt" \
  bash --noprofile --norc -eo pipefail fetch_pr_diff.sh
gh: some API error occurred (simulated)
exit code: 1
$ wc -c < gh_output_fail.txt
0
```

The command substitution `DIFF="$(gh pr diff ...)"` does not itself
trigger `-e` (command substitution exit status is captured, not
propagated, per bash semantics) — but the step's own `run:` script never
attempts to swallow it (no `||`, no `2>/dev/null` on that line, confirmed
by direct reading and by the repo's own
`test_fetch_pr_diff_does_not_swallow_gh_command_failure`), and because
`gh` here fails with empty stdout, the very next line's `[ -z "$DIFF" ]`
check catches it and `exit 1`s. The script genuinely stops — no output is
written, matching the same observable behavior. **PASS**, with the
following nuance disclosed rather than glossed over: `bash -eo pipefail`'s
own `-e` does not by itself abort on a failing command inside `$(...)`
assigned to a variable; the actual fail-safety in this specific step comes
from the explicit `-z "$DIFF"` empty check that follows, which happens to
catch both "gh failed and produced no output" and "gh succeeded but
returned nothing." A `gh` that failed non-zero while still emitting
non-empty stdout on failure (not the case for the real `gh pr diff`, which
writes errors to stderr) would not be caught by this specific mechanism —
this is a theoretical edge the current script does not need to handle
because `gh`'s own error-reporting convention (errors to stderr, empty
stdout on failure) makes it moot in practice, but it is worth naming as a
structural note rather than silently assuming `-eo pipefail` alone
accounts for the observed pass.

### 5. Delimiter randomization

Environment check:

```
$ [ -e /proc/sys/kernel/random/uuid ] && echo PRESENT || echo ABSENT
ABSENT (Linux-only feature; this is MSYS/Git-Bash on Windows, not the real
Ubuntu Actions runner)
```

**This environment cannot exercise the primary `/proc/sys/kernel/random/uuid`
path** — that path does not exist here, so every run in this validation
session fell through to the `$RANDOM`-based fallback via the script's own
`2>/dev/null || echo ...` construct. This is disclosed explicitly: what
follows proves the fallback branch works correctly and proves the overall
`DELIM=...` line degrades safely when the primary source is unavailable,
but it does **not** independently confirm uuid-based generation on the
real `ubuntu-latest` runner (a well-documented kernel feature since Linux
3.17, but not verified live here).

isolated subshell:

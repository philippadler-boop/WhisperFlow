## Requirement

> T005 Implement `SubtitleLine` and `SubtitleFile` data classes plus `.srt`
> composition (via the `srt` library) in `src/subtitles/models.py` — shared
> by US1 (creates) and US2 (edits) (data-model.md — SubtitleLine/
> SubtitleFile; spec FR-006)

Cross-checked against `data-model.md`'s SubtitleLine/SubtitleFile tables and
spec.md before validating:

- **FR-006**: "System MUST write the generated subtitles to a subtitle file
  in a standard subtitle format" — the Assumptions section fixes that format
  to `.srt`.
- **FR-008** ("no detectable speech" is a valid, successful outcome): per
  data-model.md's Transcript validation rules, an empty `segments`/`lines`
  list must compose cleanly, not error.
- **FR-009/FR-010** (review/edit): data-model.md's `SubtitleLine.edited`
  field exists specifically so "review tooling ... can distinguish generated
  vs. corrected lines," and `text` is the only user-editable field —
  timings are fixed at generation time.

This decomposes into 6 checkable sub-requirements (matching the QA task
prompt):

1. `SubtitleLine`/`SubtitleFile` import and construct directly from
   `src.subtitles.models` (well, `subtitles.models` — see note below).
2. A `SubtitleFile` of 2-3 `SubtitleLine`s composes to genuinely valid,
   independently-parseable `.srt` text.
3. `with_text()` changes only `text`, leaves timings identical, and only
   flips `edited` to `True` on an actual value change.
4. An empty `SubtitleFile` composes to `""` (FR-008).
5. `.write()` creates a real file on disk with the expected content.
6. The full test suite passes.

**Note on import path**: the task/PR title says `src.subtitles.models`, but
the project uses a src-layout editable install (`pyproject.toml`'s
`[tool.setuptools.packages.find] where = ["src"]`), so the actually-correct,
installed import path is `subtitles.models` (confirmed importable both ways
are not equivalent — `import src.subtitles.models` fails; `import
subtitles.models` succeeds after `pip install -e .`, which this repo already
has done). This matches how `tests/unit/test_subtitles_models.py` imports it
(`from subtitles.models import ...`) and is not a defect — just a nit in how
the task text is phrased.

### 3. `with_text()` semantics — identity, equality, and the `edited` flag

Independently probed (not the PR's assertions):

```
[PASS] with_text returns a different object when text changes
[PASS] with_text changed .text -- got 'Corrected text'
[PASS] with_text left start_seconds identical -- orig=2.0 changed=2.0
[PASS] with_text left end_seconds identical -- orig=5.0 changed=5.0
[PASS] with_text flips edited True on the returned object
[PASS] with_text does NOT mutate the original object's text
[PASS] with_text does NOT mutate the original object's edited flag
```

Then called `with_text()` a **second** time, with the *same* value already
on an edited line, and separately probed the same-value case starting from
`edited=False`:

```
[PASS] with_text called again with same value does not raise/crash
[PASS] with_text same-value call keeps edited True (already-true stays true) -- got True
[PASS] with_text same-value call returns identical object (no-op / same identity) -- is same object: True
[PASS] with_text with unchanged text from edited=False leaves edited False -- got False
[PASS] with_text with unchanged text returns same identity (true no-op)
```

Confirms `with_text()` is implemented as a genuine no-op (`return self`,
verified via `is` identity, not just equality) when the new text equals the
current text — `edited` is only ever set to `True` as a result of an actual
text change, and is never reset back to `False` by a subsequent
unchanged-value call (consistent with data-model.md: "True once a user has
changed `text`"). Timings (`start_seconds`/`end_seconds`) are bit-for-bit
identical between original and edited copies in every case — confirming
FR-010's "timings are not user-editable in v1" is actually enforced by the
code, not just documented. **PASS.**

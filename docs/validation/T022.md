## Requirement

> T022: Integration test: `--review` with a simulated editor that changes
> one line → finalized `.srt` reflects the edit (quickstart.md Scenario 3)
> in `tests/integration/test_review.py`

Source documents cross-checked before validating:

- `quickstart.md` Scenario 3 (FR-009, FR-010 / User Story 2):
  `whisperflow transcribe samples/hello.mp4 --review --editor "code
  --wait"` — "The command pauses after generating a draft `.srt`, opens it
  in the given editor, and waits. Edit the text of one subtitle line, save,
  and close. **Then**: the finalized `hello.srt` contains the edited text
  for that line, not the originally generated text."
- `spec.md` FR-009: "Users MUST be able to review the text of generated
  subtitle lines before treating the output as final."
- `spec.md` FR-010: "Users MUST be able to edit the text of individual
  subtitle lines, with edits reflected in the exported subtitle file."

This decomposes into the following independently checkable
sub-requirements:

1. `tests/integration/test_review.py` exists and its single test genuinely
   exercises Scenario 3's user journey: real CLI invocation, `--review`,
   an editor that changes exactly one subtitle line's text, and an
   assertion that the *finalized* file reflects the edit, not the original
   transcription.
2. The "simulated editor" is invoked the same way a real editor would be —
   as a real subprocess launched by the production `_run_editor_subprocess`
   code path — not a mock or a direct call into `review_subtitle_file`'s
   internals bypassing the CLI.
3. `pytest tests/integration/test_review.py -v` actually passes when run
   directly on this machine (not assumed from CI).
4. The test has real assertion teeth: it would fail if the review/edit
   wiring were broken (i.e., it isn't a tautology that passes regardless
   of whether edits are actually applied).
5. The full suite (`pytest -q`) still passes — no regression introduced.

## Evidence

### 1. The test genuinely exercises quickstart.md Scenario 3

Read in full (`tests/integration/test_review.py`, 121 lines). The single
test, `test_review_with_simulated_editor_reflects_edit_in_finalized_srt`:

- Copies the repo's real `clear_speech.mp4` fixture into a fresh
  `tmp_path` (not a stub/zero-length file).
- Writes a small standalone Python script (`simulated_editor.py`) that
  parses the draft `.srt` with the real `srt` library, replaces **only**
  `subtitles[0].content` with `_EDITED_TEXT = "Reviewed and corrected
  text."`, and re-writes the file — i.e., changes the text of exactly one
  subtitle line, matching Scenario 3's "Edit the text of one subtitle
  line, save, and close."
- Invokes the real CLI via `CliRunner().invoke(app, ["transcribe",
  str(video_path), "--model", "tiny", "--review", "--editor",
  editor_command])` — the exact `--review --editor <cmd>` shape Scenario 3
  documents (substituting a real, quoted `"<python>" "<script.py>"` for
  `"code --wait"` so the test doesn't depend on VS Code being installed).
- Asserts `exit_code == 0`, the finalized `.srt` exists, contains exactly
  one subtitle block, that block's **content equals `_EDITED_TEXT`** (the
  edit, not the original transcription), and that start/end timing is
  unchanged (FR-010: "only text is user-editable in v1").

This is a faithful, non-trivial exercise of Scenario 3 end to end: real
video → real ffmpeg audio extraction → real `faster-whisper` (`tiny`)
transcription → real draft write → real subprocess "editor" mutating the
file on disk → real re-read/fold-back → real finalized write → assertion
on the file actually left on disk. **Sub-requirement 1: PASS.**

### 2. The simulated editor is a genuine subprocess, not a mock

Read `src/cli/main.py`'s `_run_pipeline` and `transcribe`: the CLI's
`--review` branch calls `review_subtitle_file(subtitle_file,
editor=editor)` with **no** `run_editor` argument passed. Read
`src/cli/review.py`: `review_subtitle_file`'s `run_editor` parameter
defaults to `_run_editor_subprocess` (line 126: `if run_editor is None:
run_editor = _run_editor_subprocess`), which calls `subprocess.run(command,
check=False)` (line 188) — a real OS-level process launch, blocking until
it exits, exactly as the module's own docstring describes ("A blocking
editor invocation... is itself the confirmation"). `test_review.py` never
imports or references `run_editor`, `_run_editor_subprocess`, or
`review_subtitle_file` directly, and never monkeypatches `cli.main` or
`cli.review` — confirmed by grepping the test file for `monkeypatch`,
`mock`, `patch` (none present) and by reading `tests/conftest.py`'s
`cli_runner` fixture, which is a bare `CliRunner()` with no stubbing
(distinct from the `captured_pipeline_call` fixture other CLI tests use to
stub `_run_pipeline` — `test_review.py` uses neither `captured_pipeline_call`
nor any equivalent of its own). The `editor_command` string built by the
test (`f'"{sys.executable}" "{editor_script}"'`) is also run through the
same `_split_editor_command`/quote-stripping logic (`src/cli/review.py`
lines 141–173) that a real `--editor "code --wait"` value goes through in
production — this is genuinely the production dispatch path, not a
parallel/simplified one built for the test. **Sub-requirement 2: PASS.**

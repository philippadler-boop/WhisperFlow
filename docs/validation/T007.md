### 5. `--editor` default resolution, real shell environment variables

First, via genuinely exported shell environment variables (not a mocked
env, not `CliRunner`'s `env=` isolation) read directly through the real
`_default_editor()` function:

```
$ export EDITOR="shell_real_nano"; export VISUAL="shell_real_vim"
$ python -c "...; print(_default_editor())"
shell_real_nano

$ unset EDITOR
$ python -c "...; print(_default_editor())"
shell_real_vim

$ unset VISUAL
$ python -c "...; print(_default_editor())"
None
```

Precedence confirmed with real environment state: `$EDITOR` wins over
`$VISUAL` when both are set, falls back to `$VISUAL` when `$EDITOR` is
unset, and resolves to `None` when neither is set (per the module's own
documented fallback — the "built-in fallback prompt" itself is a later
task's job, T020's `src/cli/review.py`, which doesn't exist yet).

Then confirmed the real console script doesn't crash with `$EDITOR`
genuinely exported in the shell (same fatal-stub behavior as check 2):

```

$ whisperflow transcribe /c/tmp/qa_t007/fake_video.mp4
EXIT:1
NotImplementedError: whisperflow transcribe: pipeline not yet implemented (see T013/T014)
```

Then, via the probe script's `CliRunner(env=...)` path (which genuinely
sets and restores `os.environ` for the duration of the call — not a pure
mock) to see the value the CLI's parse path actually resolves, since the

```
EDITOR=nano_editor VISUAL=vim_editor, no --editor -> editor='nano_editor'
```

`--editor` correctly takes precedence over both environment variables
when explicitly given. All four precedence cases match
`contracts/cli.md`'s "`$EDITOR`/`$VISUAL`, else a built-in fallback
prompt" row (the fallback prompt itself being explicitly out of scope
for this skeleton). **PASS.**

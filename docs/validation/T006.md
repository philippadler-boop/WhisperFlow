## Requirement

> T006 Implement the `ProcessingJob` stage model (`ExtractingAudio` →
> `Transcribing` → `WritingSubtitles` → `AwaitingReview` → `Done`/`Failed`)
> and a stderr stage/percentage progress reporter in `src/cli/progress.py`
> (data-model.md — ProcessingJob; spec FR-011)

Cross-checked against source documents before validating:
- `data-model.md`'s **ProcessingJob** section: states
  `ExtractingAudio → Transcribing → WritingSubtitles → AwaitingReview (if
  the interactive review step runs) → Done`, with `Failed` reachable from
  any stage; state held only in process memory (no resume); percentage
  derived from `current_segment_end_seconds / video.duration_seconds`
  while `Transcribing`.
- `contracts/cli.md`'s **Progress contract (FR-011)**: while `Transcribing`,
  a completion percentage is printed to stderr; each stage transition
  (`Extracting audio…`, `Transcribing…`, `Writing subtitles…`) gets a
  single stderr line; stdout is never polluted with progress noise (the
  `.srt` file is written to `--output`, not stdout).
- `spec.md` FR-011: "System MUST show the user ongoing progress (e.g.,
  percent complete or elapsed time) while a video is being processed."

This decomposes into the 6 checks given in the task prompt.

### 5. `ProgressReporter` real stderr output matches contracts/cli.md's Progress contract

**5a. Real file-backed stream** (not `io.StringIO` — an actual file
opened on disk, bytes read back afterward):

```python
with open(OUT_PATH, "w", encoding="utf-8", newline="") as f:
    job = ProcessingJob(video_duration_seconds=120.0)
    reporter = ProgressReporter(job, stream=f)
    reporter.announce_stage(Stage.EXTRACTING_AUDIO)
    reporter.announce_stage(Stage.TRANSCRIBING)
    reporter.report_progress(30.0)   # 30/120 = 25.0%
    reporter.report_progress(60.0)   # 60/120 = 50.0%
    reporter.report_progress(120.0)  # 120/120 = 100.0%
    reporter.announce_stage(Stage.WRITING_SUBTITLES)
    reporter.announce_stage(Stage.DONE)
```

Actual raw bytes read back from disk (`repr()`):

```
b'Extracting audio\xe2\x80\xa6\nTranscribing\xe2\x80\xa6\n\rTranscribing\xe2\x80\xa6  25.0%\rTranscribing\xe2\x80\xa6  50.0%\rTranscribing\xe2\x80\xa6 100.0%\nWriting subtitles\xe2\x80\xa6\nDone.\n'
```

(`\xe2\x80\xa6` is the UTF-8 encoding of `…`, U+2026.) Decoded and
visualized:

```
Extracting audio…[LF]
Transcribing…[LF]
[CR]Transcribing…  25.0%[CR]Transcribing…  50.0%[CR]Transcribing… 100.0%[LF]
Writing subtitles…[LF]
Done.[LF]
```

This is a byte-for-byte match against contracts/cli.md's Progress
contract: each of `Extracting audio…`, `Transcribing…`, `Writing
subtitles…` is its own single stderr line; the percentage is refreshed
**in place** with a real `\r` (not accumulated as three separate lines);
percentages are correctly derived (`25.0%`, `50.0%`, and `100.0%` for
`30/120`, `60/120`, `120/120`). **PASS.**

`report_failure` correctly closes the open in-place percentage line with

**5c. Real OS-level stderr, in a genuine subprocess**, using
`ProgressReporter`'s *default* `stream=sys.stderr` argument (not an
injected stream), to confirm the default construction path actually
reaches process stderr and never leaks into stdout:

```python
CHILD_CODE = """
job = ProcessingJob(video_duration_seconds=50.0)
reporter = ProgressReporter(job)  # default stream=sys.stderr
reporter.announce_stage(Stage.EXTRACTING_AUDIO)
reporter.announce_stage(Stage.TRANSCRIBING)
reporter.report_progress(25.0)
reporter.announce_stage(Stage.WRITING_SUBTITLES)
reporter.announce_stage(Stage.DONE)
print("THIS_IS_STDOUT_NOT_STDERR")
"""
result = subprocess.run([sys.executable, "-c", CHILD_CODE], capture_output=True, text=False)
```

Actual captured OS pipes:

```
child STDOUT (raw): b'THIS_IS_STDOUT_NOT_STDERR\r\n'
child STDERR (raw): b'Extracting audio\x85\r\nTranscribing\x85\r\n\rTranscribing\x85  50.0%\r\nWriting subtitles\x85\r\nDone.\r\n'
```

Confirmed: `THIS_IS_STDOUT_NOT_STDERR` appears only in stdout, never in
stderr, and none of the stage/percentage text leaks into stdout —
matching the contract's "Machine-readable output ... is never mixed into
stdout progress noise." **PASS**, subject to one environment observation
below.

**Observation (not a contract violation, not blocking T006):** on first
attempt, decoding the subprocess's captured stderr bytes as UTF-8 raised
`UnicodeDecodeError` (`\x85` is not a valid UTF-8 continuation byte). This
is a property of this Windows box, not a defect in `progress.py`: when a
Python process's stdout/stderr are redirected to a pipe rather than a
console, Python 3.12 on Windows falls back to the process's ANSI code
page (`cp1252` here, confirmed via `sys.stdout.encoding` in a matching
subprocess check) rather than UTF-8, and `cp1252` happens to have a
direct single-byte mapping for `…` (U+2026) at `0x85` — a different
encoding of the same character, not corruption. Decoding the same bytes
as `cp1252` reproduces the exact same text as the UTF-8 file-based check
above (`Extracting audio…`, `Transcribing…  50.0%`, `Writing
subtitles…`, `Done.`). Separately, Python's `sys.stderr` always defaults
to `errors="backslashreplace"` (confirmed directly:
`sys.stderr.errors == 'backslashreplace'` in this environment), so even
on a code page with no ellipsis mapping at all, printing `…` would never
raise `UnicodeEncodeError` and crash the reporter — worst case it would
render as a literal `…` escape instead of `…`. `contracts/cli.md`
does not mandate a specific stderr encoding, and this repo's CI runs on
`ubuntu-latest` with a UTF-8 locale (T003's report confirms the CI
environment), where this doesn't arise. Flagging only as a
cross-platform-consumption note for whoever eventually pipes/logs this
CLI's stderr on Windows without forcing UTF-8 — not a T006 failure.

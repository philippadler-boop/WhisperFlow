## Requirement

> T021: Wire `--review`/`--no-review` branching into the CLI command,
> defaulting to `--review` per `contracts/cli.md`, in `src/cli/main.py`
> (depends on T014, T020) (spec FR-005)

Source documents cross-checked before validating:

- `spec.md` FR-005: "System MUST expose subtitle generation through a
  command-line interface for v1."
- `spec.md` FR-009/FR-010 (what the `--review` branch must actually
  deliver): review before finalizing, and edits reflected in the exported
  file.
- `contracts/cli.md`'s Options table: `--review / --no-review`, default
  `--review`; "With `--review`, after generating a draft `.srt` the
  command opens it in `$EDITOR` (or `--editor`) and waits for confirmation
  before finalizing... `--no-review` finalizes immediately."
- `contracts/cli.md`'s Exit codes section: fatal errors reported as a
  single human-readable stderr line, exit code 1.

This decomposes into the following independently checkable
sub-requirements:

1. With no `--review`/`--no-review` flag given, the command defaults to
   `--review` and actually enters the review flow (opens the configured
   editor, blocks, and folds the edit into the finalized `.srt`).
2. `--no-review` skips the review step entirely and leaves the pipeline's
   own raw output as the final `.srt`, with no editor ever launched.
3. A write-back failure after a successful review (the specific gap the
   PR #122 review round found and the developer fixed) is reported as a
   single `Error: ...` line and exit code 1, not a raw traceback — proving
   the fix actually works, not just that the reviewer's finding text was
   addressed.
4. `whisperflow transcribe --help`'s documented default for
   `--review`/`--no-review` matches `contracts/cli.md`.
5. `pytest tests/unit/test_cli_main.py -v` and the full suite actually
   pass when run directly (not assumed from the PR description or CI).

### 1. Default (no flag) enters the review flow and folds the edit into the finalized file

Command (a fake editor script that rewrites the draft's spoken text,
launched exactly the way `--editor`/`$EDITOR` would launch a real editor):

```
$ whisperflow transcribe clip.mp4 --model tiny --editor "python C:\...\fake_editor.py"
Extracting audio…
Transcribing…
Transcribing…  91.7%
Writing subtitles…
Done.
$ echo $?
0
$ cat clip.srt
1
00:00:00,000 --> 00:00:03,200
QA-EDITED-Hello, this is a test on the whisper flow sub-title generator.
```

No `--review`/`--no-review` flag was passed at all, yet the fake editor
was invoked (its rewrite — prefixing "Hello" with `QA-EDITED-`) — is
present in the *finalized* file on disk, proving: (a) the default is to
enter the review branch, (b) the draft the editor operated on was the
pipeline's own real transcription output (confirmed by comparing against
sub-requirement 2's raw output below, which reads verbatim "Hello, this is
a test..."), and (c) the edited result, not the original draft, is what
gets written back to `output_path`. **Sub-requirement 1: PASS.**

### 2. `--no-review` skips the review step; pipeline output used as-is

Command (no `--editor` involvement at all — if the review path were
mistakenly entered without an editor configured, this would have blocked
on stdin waiting for a fallback-prompt confirmation instead of exiting
cleanly):

```
$ whisperflow transcribe clip.mp4 --model tiny --no-review
Extracting audio…
Transcribing…
Transcribing…  91.7%
Writing subtitles…
Done.
$ echo $?
0
$ cat clip.srt
1
00:00:00,000 --> 00:00:03,200
Hello, this is a test on the whisper flow sub-title generator.
```

The command completed without blocking (proving no fallback prompt/editor
was invoked) and the output contains the raw, un-mutated transcription —
no `QA-EDITED-` marker, matching sub-requirement 1's draft text before the
fake editor's rewrite. **Sub-requirement 2: PASS.**

### 3. Write-back `OSError` → `SubtitleWriteError` fix actually works end-to-end

To exercise the exact code path the PR #122 review flagged
(`subtitle_file.write()` after `review_subtitle_file()` in `src/cli/
main.py`'s `_run_pipeline`), a second fake editor script edits the draft
and then `chmod`s the output file read-only *before returning* — so the
CLI's own write-back (which runs immediately after the editor process
exits) hits a genuine `PermissionError` (an `OSError` subclass), not a
mocked one:

```
$ whisperflow transcribe clip.mp4 --model tiny --review --editor "python C:\...\fake_editor_readonly.py" --output clip_c.srt 1>stdout.log 2>stderr.log
$ echo $?
1
=== STDOUT ===
(empty)
=== STDERR ===
Extracting audio…
Transcribing…
Transcribing…  91.7%
Writing subtitles…
Done.
Error: failed to write subtitle file to 'clip_c.srt': [Errno 13] Permission denied: 'clip_c.srt'
```

Exit code 1, exactly one line beginning `Error:`, no Python traceback
anywhere in stdout or stderr, and the message text matches
`SubtitleWriteError`'s format (`failed to write subtitle file to
'{path}': {reason}`) — proving the `try: subtitle_file.write() except
OSError as exc: raise SubtitleWriteError(...)` guard added in `ec4ee91`
genuinely converts a real `OSError` into the documented single-line,
exit-code-1 error, not merely that a unit test mocking `SubtitleFile.write`
to raise `OSError` passes. Before this fix (per the PR's own review
history), this same scenario would have surfaced as a raw, unhandled
`PermissionError` traceback instead. **Sub-requirement 3: PASS.**

(Read-only permission bit on the scratch output file was reset and the
file removed immediately after this test; nothing was left behind.)

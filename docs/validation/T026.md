## Requirement (source of truth)

**quickstart.md Scenario 7 — Local-only processing (FR-004)**:

> Run Scenario 1 with outbound network access blocked (e.g. via a firewall
> rule or a network namespace with no route). **Expected**: Identical
> success and output to Scenario 1 — no failure is attributable to a
> blocked network call, confirming no transcription traffic ever leaves
> the machine.

**spec.md FR-004**: "System MUST perform all transcription processing
locally, on the user's own machine; video/audio content MUST NOT be
transmitted to a cloud or third-party service."

This decomposes into the sub-requirements checked below:

1. The test file exists at `tests/integration/test_no_network.py` and
   genuinely blocks outbound network at the socket layer (not one HTTP
   client) for `connect`, `connect_ex`, `create_connection`, and
   `getaddrinfo`.
2. Running the test file confirms `transcribe` succeeds identically to
   Scenario 1 (same exit code, same `.srt` content — text *and* timing)
   with the network blocked.
3. The fixture-ordering fix (`blocked_network` structurally depending on
   session-scoped `warm_model_cache`) actually guarantees "cache warmed
   before network blocked," not just by accident of file/test collection
   order — stress-tested including a genuinely cold cache.
4. The positive-control test genuinely proves the blocking mechanism works
   for all four patched entry points.
5. No regressions in the broader suite.

## Evidence

### 1. Read the full test file and its blocking mechanism

Read `tests/integration/test_no_network.py` (216 lines) in full on
`20ec278`. Confirms:

- `blocked_network` (lines 97–123) patches `socket.socket.connect`,
  `socket.socket.connect_ex`, `socket.create_connection`, and
  `socket.getaddrinfo` — all four documented entry points, at the raw
  socket layer, not a single HTTP client mock.
- `blocked_network`'s signature is
  `blocked_network(monkeypatch, warm_model_cache: None)` — it takes
  `warm_model_cache` as a fixture parameter, which is pytest's
  fixture-dependency mechanism, not a body-level function call.
- `warm_model_cache` (lines 80–95) is `scope="session"` and calls
  `_prewarm_model_cache()`, which constructs a real
  `faster_whisper.WhisperModel("tiny", ...)` — the same construction path
  `transcription.transcribe._load_model` uses per the docstring — with the
  network still unpatched.
- The test body
  (`test_clear_speech_video_transcribes_identically_with_network_blocked`,
  lines 154–216) no longer calls `_prewarm_model_cache()` itself (this was
  the CRITICAL review finding); it only depends on `blocked_network`,
  which transitively pulls in `warm_model_cache`.

**PASS** — matches the claimed structural fix.

### 4. Positive-control test covers all four patched entry points

Read `test_blocked_network_fixture_actually_blocks_outbound_connections`
(lines 126–151): asserts `pytest.raises(OSError)` around
`socket.create_connection(...)`, a raw socket's `.connect(...)`, and that
same raw socket's `.connect_ex(...)` — three of the four patched
callables exercised directly — then asserts `blocked_network.attempts >=
3`, confirming the blocker's call counter actually incremented for each,
not just that no exception escaped. `getaddrinfo` is patched by
`blocked_network` (line 122) but is not separately exercised by this
positive-control test — it's only implicitly exercised inside the real
`transcribe` run in the second test (DNS resolution would occur before any
HTTP connection). This is a minor completeness gap: the positive control
directly proves 3 of 4 patched entry points fire, and relies on the second
test to indirectly cover `getaddrinfo`. **PASS with a minor caveat** — not
a blocking issue since the entry point is patched and the real pipeline
exercises it, but the positive control's own docstring ("Exercises all
three patched entry points individually") is accurate only for 3 of the 4
now-patched targets, which is a slightly stale claim given `getaddrinfo`
was added in the same review round.

## Overall: PASS

The test genuinely proves what Scenario 7 and FR-004 require: a real
`transcribe` run produces identical output (text and timing) whether or
not the network is reachable, and the network-blocking mechanism is
verified independently of `transcribe`'s own behavior. Critically, the
fixture-ordering fix from the review round was not just re-read and
trusted — it was stress-tested against a genuinely cold model cache (real
network download observed happening into an empty scratch `HF_HOME`
before the socket patches took effect), and the pre-fix version was
independently reproduced from history and shown to fail under those exact
conditions with the precise `LocalEntryNotFoundError` /
"outbound network access is blocked" symptom the review predicted. That is
direct evidence the fix is structural, not incidental. One minor,
non-blocking documentation/completeness gap is noted (the positive control
doesn't individually exercise the fourth patched entry point,
`getaddrinfo`) but does not undermine the requirement, since `getaddrinfo`
is exercised as part of the real pipeline in the second test and is
correctly patched.

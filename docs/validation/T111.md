```
Independently review pull request #999's diff, embedded
verbatim below between the "--- BEGIN DIFF ---" and

The diff above is the complete, authoritative change set for
this pull request, already fetched by this workflow via
"gh pr diff". Do not attempt to re-derive, re-fetch, or
reconstruct it yourself -- you have no Bash, git, or gh tool
capable of doing that reliably, and none is granted to you in

This repository has already been checked out locally at this
pull request's own head commit. Use your Read, Grep, and Glob

Your response MUST begin with a machine-readable verdict line as

one of these two literal strings, character-for-character, and

VERDICT: APPROVE
VERDICT: REQUEST_CHANGES

Use "VERDICT: APPROVE" if and only if you are approving the PR
outright, with no requested changes. Use
"VERDICT: REQUEST_CHANGES" if you are requesting any changes at
all, however small. Do not write any paraphrase, summary, or
variation of these strings (e.g. not "Verdict: Approve", not
"VERDICT: Approved", not "My verdict is APPROVE", not
"VERDICT: APPROVE - looks good") -- an automated step
downstream matches this line by exact literal string comparison
and will fail the workflow visibly if it does not match either
literal exactly. After that first line, write your full
human-readable report (approval rationale, or the specific
actionable points) on subsequent lines exactly as described
above.
PROMPT_EOF_5302770723075
```

**Read end to end as a careful reader (not just grepped for "VERDICT")**:
the prompt opens with clear task framing (review this diff, no other
context), embeds the diff between unambiguous `--- BEGIN/END DIFF ---`
markers, gives explicit tool-usage constraints, then states the
review-report deliverable ("Produce your review report... either approve,
or request changes..."), and only after that introduces the verdict-line
requirement as an additional, layered requirement — not a replacement.
The verdict instruction itself is placed as the last block of instructional
text immediately before the model's response begins, which is a sensible
position for a "this must be the literal first line of your response"
requirement (nothing comes after it to push the model's attention away
from it). The instruction:
- states the positional constraint explicitly and strongly ("MUST begin...
  no preamble, blank line, heading, or other text before it");
- gives the two literal strings on their own lines, described as "literal
  strings, character-for-character, and nothing else on the line";
- disambiguates *which* to use ("if and only if... with no requested
  changes" vs. "if you are requesting any changes at all, however small"),
  closing off the ambiguous middle ground a real reviewer might otherwise
  hedge on;
- gives four concrete negative examples of near-miss phrasing to reject
  (case variation, past tense, narrative framing, trailing commentary);
- states the consequence of a mismatch (exact string comparison, visible
  workflow failure) — this gives the model a concrete reason to comply
  literally rather than treating it as a soft suggestion.

This reads as genuinely unambiguous in context. **PASS**, with one
observation matching the prior reviewer's non-blocking note: the four
negative examples do not include a markdown-wrapped variant (e.g.
`**VERDICT: APPROVE**`), which a model might plausibly produce given how
often bold/emphasis is used for headings in free-form prose elsewhere in
its own output. This does not make the instruction ambiguous as written —
the "character-for-character... nothing else on the line" language already
technically rules out markdown wrapping — but it is a real gap in the
example list that a downstream literal-string parser (T112/T113) could
trip on in practice. Flagged here as a suggestion, not a fail, since T111
is scoped to unambiguous instructional text and that requirement is met.

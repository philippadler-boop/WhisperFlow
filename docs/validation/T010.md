### 2. Independently forced failure modes: temp-file leak and "ffmpeg exited 0 with no output"

Two scenarios from the reviewer's round-1 findings, re-driven from
scratch against a hand-rolled `subprocess.run`/`shutil.which` fake (not
copied from the test file):

| Scenario | Method | Result |
|---|---|---|
| (a) `ffmpeg` disappears mid-call (`FileNotFoundError` race), `output_path=None` (owned temp file) | `subprocess.run` mocked to raise `FileNotFoundError`; OS temp dir scanned for `whisperflow_*.wav` before and after | **PASS** — `FfmpegNotFoundError` raised, and the before/after temp-dir diff is empty: no leaked file. Confirms the round-1 leak (`resolved_output.unlink()` previously only ran in the `returncode != 0` branch) is genuinely fixed. |
| (b) `ffmpeg` exits 0 without creating the output file at all, `output_path=None` (owned temp file) | `subprocess.run` mocked to return `returncode=0` without touching the output path | **PASS** — `AudioExtractionError` raised (`"ffmpeg exited successfully but produced no output audio file"`), not a bogus `AudioTrack`; no leaked temp file. |
| (b) `ffmpeg` exits 0 and writes a 0-byte file, `output_path=None` | `subprocess.run` mocked to write `b""` to the output path, `returncode=0` | **PASS** — `AudioExtractionError` raised. |

**PASS for the owned/auto-generated-temp-path case** — this matches
exactly what the reviewer's round-1 comment and the fix's own regression
tests exercise, and it is also the actual call pattern the codebase uses
in practice (`extract.py`'s own docstring: the T013 pipeline is expected
to call `extract_audio(video)` with `output_path=None` and manage
cleanup itself).

**Additional finding — gap in the same fix for a caller-supplied,
pre-existing `output_path`** (constructed independently, not part of the
task's minimum ask, but directly relevant to "confirm `AudioExtractionError`
is raised rather than a bogus `AudioTrack`"): when `output_path` is
caller-supplied *and already exists with non-empty content* (e.g. a
stale file from a prior run at the same path), and `ffmpeg` exits 0
without touching that path at all, `extract_audio()` does **not** raise
`AudioExtractionError` — it silently returns a "successful" `AudioTrack`
pointing at the stale, unrelated bytes:

```
--- Scenario B: caller_output pre-exists with stale non-empty content ---
NO EXCEPTION RAISED -- got AudioTrack: AudioTrack(..., extracted_path=WindowsPath('.../stale_output.wav'), sample_rate_hz=16000)
  track.extracted_path == caller_output2: True
  content is still the STALE bytes: b'STALE AUDIO DATA FROM A PREVIOUS SUCCESSFUL RUN, NOT EMPTY'
```

Root cause: the fix's guard (`if not resolved_output.exists() or
resolved_output.stat().st_size == 0`) only checks *existence and size*,
which for an auto-generated `mkstemp()` path is a reliable proxy for
"`ffmpeg` actually wrote something" (that file starts empty by
construction, every time). For a caller-supplied path, existence/size
predate the `ffmpeg` call entirely and are not reliable evidence of
anything `ffmpeg` did on *this* call. A parallel, freshly-constructed
control run (Scenario A, same mock, but `caller_output` does not
pre-exist) correctly raises `AudioExtractionError` — confirming the gap
is specifically about *pre-existing* caller paths, not caller paths in
general.

This is a real, reproducible gap in the exact fix the reviewer approved,
though it sits outside both the reviewer's original two findings and the
codebase's current actual call pattern (T013 always uses the
auto-generated path per `extract.py`'s own docstring) — recorded here as
evidence, not fixed by this report per `qa` scope.

### 3. `FfmpegNotFoundError` via genuine PATH manipulation

`shutil.which` was **not** mocked for this check. Instead, `ffmpeg`'s
real directory was stripped out of the real `os.environ["PATH"]` at
runtime, confirmed via `shutil.which` before/after, and `subprocess.run`
was patched only to raise `AssertionError` if called at all (to prove
the function short-circuits *before* ever invoking the subprocess):

```
ffmpeg resolves (before PATH edit): C:\ProgramData\chocolatey\bin\ffmpeg.EXE
ffmpeg resolves (after stripping its dir from PATH): None
PASS: FfmpegNotFoundError genuinely raised: required 'ffmpeg' binary was not found on PATH (install ffmpeg and ensure it is on PATH)
restored PATH resolves ffmpeg again: C:\ProgramData\chocolatey\bin\ffmpeg.EXE
```

**PASS** — `FfmpegNotFoundError` is raised under a genuinely-missing
binary (real PATH edit, not a mock), and `subprocess.run` was confirmed
never called. The process's real `PATH` was restored immediately after.

### 4. Caller-supplied `output_path` is never deleted on failure

Tested against all three of `extract_audio()`'s failure branches (task
asked for at least two), each independently constructed:

| Failure branch | Setup | Result |

Deletion-wise: **PASS** (nothing was ever deleted). Correctness-wise: this is the same gap as §2. |

**PASS** on the literal "never deleted" requirement across all three

caller-supplied path is structurally never passed to `.unlink()`
anywhere in `extract.py`, confirmed empirically in all three branches,
not just read from the source.

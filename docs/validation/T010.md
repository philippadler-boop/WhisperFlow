### 2. Previously-recorded gap re-verified as closed: caller-supplied, pre-existing `output_path` + `ffmpeg` exiting 0 without writing anything

**Background** (from this report's first version): with the fix that
had just been reviewed at the time, `extract_audio()` verified "did
`ffmpeg` write output?" by checking `resolved_output.exists()` /
`.stat().st_size == 0` directly on `output_path` when one was
caller-supplied. That's a reliable proxy only for an auto-generated
`mkstemp()` path (guaranteed empty at the start of the call); for a
caller-supplied path with pre-existing non-empty content, it proved
nothing about what *this* call's `ffmpeg` invocation actually did. The
first-pass report constructed exactly that scenario and got a silent
"successful" `AudioTrack` pointing at stale, unrelated bytes instead of
`AudioExtractionError`.

**What changed**: three commits after that report
(`f7dfa07` → `9cdcbd8` → `5523d22`) replaced that approach with a
structural redesign, confirmed by reading the current `extract.py`
directly: `ffmpeg` is now **always** pointed at a fresh,
`tempfile.mkstemp()`-created temp path (`temp_output`), *never* at
`output_path` directly, regardless of whether the caller supplied one.
The "did `ffmpeg` write non-empty output?" check
(`if not temp_output.exists() or temp_output.stat().st_size == 0`)
therefore always runs against a path that is guaranteed empty at the
start of the call — the ambiguity that caused the gap no longer has
anywhere to enter. Only *after* that check passes does
`_finalize_output()` move the confirmed-good temp file onto
`output_path` (via `os.replace`, replacing whatever was there).

**Re-verification** — reconstructed the *exact* scenario from the first
report (caller-supplied `output_path` pre-existing with stale non-empty
content; `subprocess.run` mocked to return `returncode=0` without
writing to the path it's invoked with — which, per the redesign, is now
always `temp_output`, asserted explicitly in the mock so the check itself
can't be fooled by ffmpeg silently having been pointed at
`output_path`) against the current code (`qa_t010_regap_check.py`,
written fresh from the current source):

```
--- Scenario 1: caller output_path pre-exists with stale content, ffmpeg exits 0 writing nothing ---
PASS: AudioExtractionError raised: failed to extract audio from '...\clip.mp4': ffmpeg exited successfully but produced no output audio file
caller_output untouched (still stale bytes): True
leaked temp files: none
```

**PASS — gap closed.** `AudioExtractionError` is now genuinely raised
for the exact case that previously silently "succeeded," the caller's
pre-existing file is left completely untouched (still the original stale
bytes, not deleted and not replaced with garbage), and no owned temp
file is leaked. This isn't just fixed for this one constructed input —
the redesign makes the class of bug structurally impossible going
forward, since `output_path`'s pre-existing state can no longer factor
into the "did ffmpeg write anything?" decision at all; it's only ever
consulted (and only ever mutated) after that decision has already been
made against `ffmpeg`'s own dedicated, guaranteed-fresh temp file. The
codebase's own test suite independently arrived at the same fix and
added a directly analogous regression test
(`test_ffmpeg_success_leaving_preexisting_output_untouched_raises_extraction_error`),
read only after writing and running the script above.

### 3. New fix re-verified: broadened `OSError` handling around the `ffmpeg` launch itself

**Background**: the reviewer's final round (`5523d22` → `4e4235e`)
flagged that `extract_audio()`'s `subprocess.run()` call only caught
`FileNotFoundError`. Any other `OSError` subclass a failed process launch
can raise for a binary that **is** on `PATH` but can't actually be
started — `PermissionError` (blocked/non-executable), a corrupt or
wrong-architecture binary surfacing as a plain `OSError` — would escape
uncaught as a raw `OSError`, contradicting the function's own documented
"never a raw `OSError`" contract, and would leak the just-created
`temp_output` file (nothing on that path unlinked it).

**Re-verification** — mocked `subprocess.run` to raise `PermissionError`
(not `FileNotFoundError`) and confirmed both the exception type and
temp-file cleanup, via a script written fresh from the current source
(`qa_t010_regap_check.py`, scenario 2):

```
--- Scenario 2: subprocess.run raises PermissionError ---
PASS: AudioExtractionError raised: failed to extract audio from '...\clip.mp4': failed to run 'ffmpeg': [Errno 13] Permission denied: 'ffmpeg'
  isinstance FfmpegNotFoundError: False (must be False)
  exact type: AudioExtractionError (must be AudioExtractionError, not a subclass surprise)
leaked temp files: none
```

**PASS.** `PermissionError` is caught by the second, broader
`except OSError as exc` clause (correctly ordered *after* the narrower
`except FileNotFoundError`, confirmed by the fact that `FfmpegNotFoundError`
was *not* raised — a `PermissionError` is not a `FileNotFoundError`, so
if the clauses were misordered or the second one absent, this would have
either raised the wrong error type or escaped as a raw `PermissionError`/`OSError`
instead), is reported as `AudioExtractionError` (checked by exact type,
not just `isinstance`, to rule out it smuggling through as some other
`OSError` subclass), and the OS temp directory shows no leaked
`whisperflow_*` file before/after. The error message correctly reflects
that `ffmpeg` failed to *launch* ("failed to run 'ffmpeg': ...") rather
than reusing `FfmpegNotFoundError`'s "install ffmpeg and ensure it is on
PATH" message, which would have been actively wrong here since `ffmpeg`
is on `PATH` — it just couldn't be started.

### 4. `FfmpegNotFoundError` via genuine `PATH` manipulation, and caller-output-never-deleted — carried forward, not re-run

The first-pass report's Evidence §3 (`FfmpegNotFoundError` forced via a
real `os.environ["PATH"]` edit, not a `shutil.which` mock) and §4
(caller-supplied `output_path` never deleted, tested across all three
failure branches) exercise code paths that the four post-report commits
did not change in any way relevant to those checks: the
`shutil.which(FFMPEG_EXECUTABLE) is None` guard at the top of
`extract_audio()` is untouched, and every failure branch in the current
code still only ever calls `.unlink()` on `temp_output` — the internal,
always-owned temp file — never on `output_path`. This report does not
re-run those two checks from scratch (out of scope for this specific
re-verification pass), but notes that Evidence §2 and §3 above already
provide direct, current-code confirmation of the caller-output-never-
touched property in the two specific failure modes those scenarios
mock (a no-op `ffmpeg` exit, and a launch-time `OSError`) — in both
cases the pre-existing caller file was confirmed byte-for-byte
unchanged. The redesign, if anything, strengthens this guarantee versus
the code the first-pass report examined, since `output_path` is now
structurally never opened for writing by anything except the single,
success-gated `_finalize_output()` call.
